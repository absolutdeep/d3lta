## Why this matters

`drizzle.config.ts` points at `out: "./lib/db/migrations"` (line 6), but that
directory **does not exist** — no migrations have ever been generated. The
schema (`lib/db/schema.ts`) defines three tables (`themes`,
`user_preferences`, `audit_logs`), and the app creates them implicitly on first
use (libsql/SQLite auto-creates tables on insert). This means:

1. There's no versioned migration history, so schema changes can't be applied
   cleanly across environments.
2. A fresh checkout has no way to create the schema deterministically.
3. `ARCHITECTURE.md` §5 lists "Migration support for schema evolution" as a
   benefit of the Drizzle choice, but it's not wired up.

The fix: generate the initial migration from the current schema, and add a
`db:migrate` script so the schema can be applied deterministically.

## Steps

### Step 1: Generate the initial migration

Run:

```bash
pnpm dlx drizzle-kit generate
```

This reads `lib/db/schema.ts` and writes the initial migration SQL into
`lib/db/migrations/`.

**Verify**: `ls lib/db/migrations/` shows a `0000_*.sql` file (and a
`meta/` directory). The SQL should contain `CREATE TABLE` statements for
`themes`, `user_preferences`, and `audit_logs`.

### Step 2: Add the migration scripts to `package.json`

In `package.json` `scripts`, add:

```json
"db:generate": "drizzle-kit generate",
"db:migrate": "drizzle-kit migrate"
```

**Verify**: `grep -n "db:generate\|db:migrate" package.json` shows both scripts.

### Step 3: Wire the migration runner into the DB client (recommended)

`lib/db/client.ts` currently creates the client but never runs migrations. To
make a fresh checkout work deterministically, invoke the migration runner on
startup. Drizzle's libsql driver exposes `migrate()` from
`drizzle-orm/libsql/migrator`:

In `lib/db/client.ts`, add:

```ts
import { migrate } from "drizzle-orm/libsql/migrator";
import path from "node:path";

// In createDb(), after creating the drizzle instance:
await migrate(db, { migrationsFolder: path.join(process.cwd(), "lib/db/migrations") });
```

**Important**: `createDb()` is currently synchronous (returns `{ client, db }`).
Making it `async` changes `getDb()`'s signature, which is called synchronously
in every API route (`const db = getDb();`). Converting all callers to `await
getDb()` is a larger change. **Two options**:

- **(a) Fire-and-forget migration on startup** (preferred, minimal): in
  `createDb()`, call `void migrate(...)` without awaiting, so `getDb()` stays
  synchronous. The migration runs in the background on first import. This is
  acceptable for a local single-user tool but has a race (a query could run
  before the migration finishes).
- **(b) Make `getDb()` async** and `await` it in all callers. This is the
  correct long-term approach but touches every API route. If you choose this,
  add all the route files to the in-scope list.

Prefer **(a)** for this plan to keep the change small and low-risk. If you
choose (a), add a comment noting the race and that (b) is the follow-up.

**Verify**: `npx tsc --noEmit` exits 0.

### Step 4: Verify the migration applies

Run:

```bash
pnpm run db:migrate
```

**Verify**: exit 0; drizzle-kit reports the migration applied. The existing
`d3lta.db` (which already has the tables) should be a no-op or apply cleanly
(drizzle-kit tracks applied migrations in a `__drizzle_migrations` table).

### Step 5: Verify the full build

```bash
pnpm run lint
npx tsc --noEmit
pnpm run build
```

**Verify**: all three exit 0.

## Maintenance notes

- From now on, schema changes should follow: edit `lib/db/schema.ts`, run
  `pnpm run db:generate`, then `pnpm run db:migrate`. Commit the generated
  migration with the schema change.
- The fire-and-forget migration in `createDb()` (option a) has a startup race.
  If the app grows, convert `getDb()` to async and `await` it in callers —
  that's the follow-up.
- The `__drizzle_migrations` table tracks applied migrations; don't delete it.
- If the team deploys to a shared DB (libsql cloud), the migration runner must
  run once at deploy time, not per-request — revisit the startup-migration
  approach then.
